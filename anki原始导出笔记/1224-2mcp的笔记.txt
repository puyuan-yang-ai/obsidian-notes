AIG-Eval这个框架下，agent会执行什么样的流程？	"Agent 自己去：    - 阅读源码（source_file_path 指定的文件）    - 修改/优化 kernel    - 执行 compile_command    - 执行 correctness_command → 看输出有没有 ""PASS""    - 执行 performance_command → 记录执行时间    - 填写 task_result.yaml"

assign_score_withk.cpp  assign_score_withk_cuda.cu  assign_score_withk_cuda.hip  上面这三个文件显示了一个 CUDA → HIP 移植的场景	原始代码（NVIDIA） .cu 文件 (保留参考)  ->  移植后（AMD）.hip 文件 (待优化) ->      最终目标:优化后的 .hip(Agent 产出)
AIG-Eval里面，为什么把各个指令拼接到提示词里面来让 Agent 来决策？	"因为这个是Agent 评测框架，给 Agent 目标，让它自己决定怎么做。make → 失败 → 分析错误信息 → 修复代码 → 重新编译 → 成功。这才是评测 Agent 智能程度的意义！ 框架只告诉 Agent""你要做什么""，不告诉它""你要怎么做""。"

AIG-Eval里面，Agent 是如何被加载的？从config.yaml里面读取agent 名称为起点，加载的流程是什么？	"第 1 步：读取 config.yaml里面的agent 名称，比如“SWE-agent”， 第 2 步：module_registration.py里面，将字符串 ""SWE-agent"" 转换为 AgentType.SWE_AGENT 枚举  第 3 步：module_registration.py里面,根据枚举类型，import 对应的模块 ,导入启动器  第 4 步：launch_agent.py里面，启动器被调用 ，本质上执行subprocess.Popen(cmd, ...)   ← 调用系统命令 ""mini""               第 5 步：系统PATH里面，找到 ""mini"" 命令并执行"
AIG-Eval里面的agent目录,它们都必然包含哪个文件,然后这个文件里面大概率会包含着一个AGENT和OPTIONS这两个变量,如果存在这两个变量，那么这两个变量分别的作用是什么？	包含launch_agent.py文件作为agent启动文件，  AGENT变量呢就是用来存储对应agent的cli命令，然后OPTIONS存放的是这个cli命令的参数.

当我运行AIG-Eval的时候，选择了mini-swe-agent，这个时候这个评估框架不会读取我的这里面的mini-swe-agent项目的源码而是去相应的系统目录下面找这个已经安装好的程序是吗？以及为什么？	是的，启动评估的时候，评估框架使用的是cli命令，进而会去调用系统 PATH（如 /usr/local/bin, ~/.local/bin）里面已安装的 mini-swe-agent（通过 pip install 安装），而不是读取本地的源码目录。
AIG-Eval里面的launch_agent.py里面使用到了”mini -c /path/to/mini.yaml “这个指令，这里的mini.yaml文件，指向的是这个mini-swe-agent所在的原代码目录吗还是说在安装后的目录呀？	都不是，这个文件是在 AIG-Eval 框架内部，也就是在AIG-Eval/agents/SWE_agent/mini.yaml 这里。
运行 pip install -e . 或 pip install minisweagent 后，mini 命令被安装到系统中，如何验证这个实际被调用的路径呢？	在终端运行which mini，输出是/opt/conda/envs/xxx/bin/mini，这个路径才是 AIG-Eval 实际调用的程序。
如何确定cli命令 mini 实际调用的程序在哪里？	在终端运行：which mini，这个路径才是 AIG-Eval 实际调用的程序！
mini CLI 命令执行后是不是走对应的源代码？以及为什么？	"你在终端输入: mini --mcp -c xxx.yaml -t ""prompt""                 │                 ▼ 系统查找 PATH: which mini → ~/.local/bin/mini                 │                 ▼ 这个 mini 是一个入口脚本，指向安装后的 Python 包                 │                 ▼ 实际执行: python -m minisweagent.run.mini ...                 │                 ▼ 运行的是安装后的代码（来自你 pip install 时的那个源码目录）"
AIG-Eval里面评估mini-swe-agent的时候，为什么使用的不是mini-swe-agent源码目录下面的自身的配置文件mini.yaml？	因为AIG-Eval 通过 -c 参数强制指定了配置文件。
AIG-Eval强制指定配置文件mini.yaml而不是使用mini-swe-agent默认的配置文件，为什么 AIG-Eval 要这样设计？	因为 AIG-Eval 需要控制 Agent 的行为：从评估框架的角度来控制agent。
AIG-Eval 的 mini.yaml（通过 -c 参数指定）以及 mini-swe-agent 的 prompts.py（--mcp 模式激活）这两个文件里面都有SYSTEM_TEMPLATE 和 INSTANCE_TEMPLATE  这两个提示词，那么我的prompts.py里面的提示词还会生效吗？也就是当同时使用 -c mini.yaml 和 --mcp 时，哪个 prompt 模板会生效？以及为什么？	通过 -c 参数指定的mini.yaml里面的SYSTEM_TEMPLATE 和 INSTANCE_TEMPLATE  这两个提示词不会生效，因为当 --mcp 模式开启时，主动删除 yaml 配置文件中的 prompt 模板，让 prompts.py 中的 这两个prompt 生效！也就是，代码主动删除了 yaml 中的 prompt，让 prompts.py 的模板优先
AIG-Eval 的 mini.yaml（通过 -c 参数指定）以及 使用--mcp 模式激活 mini-swe-agent 的 prompts.py的情况下，AIG-Eval 的 mini.yaml 还有效吗？	有效果！其他配置（模型、超时等）仍然生效，只有SYSTEM_TEMPLATE 和 INSTANCE_TEMPLATE 这两个 prompt 模板被 prompts.py替换
mini --mcp 激活 MCP 模式，自动使用什么？	使用的是你的 prompts.py 中的 prompt 模板，来覆盖-c mini.yaml 里面的system_template和instance_template这两个提示词。
Cheatsheet 这部分的提示词是在AIG-Eval框架里面还是在mini-swe-agent里面？以及为什么？	在AIG-Eval里面的prompt_builder.py里面，因为Cheatsheet 属于评估框架层面给模型外加的知识库，从更宏观的角度来指导agent，类似Instructions 里面包含了各种agent可以参考的编译指令运行指令等等，Cheatsheet  这个部分是给模型执行的时候作为参考使用的。 prompt_builder.py里面包含下面这些要素：  - Task Type                                                        - Source Code  - Instructions                                                     - Output Format  - Cheatsheet   - Workspace Info

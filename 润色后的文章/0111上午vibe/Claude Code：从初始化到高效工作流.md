# Claude Code：从初始化到高效工作流

## 初始化：让 AI 理解你的项目

初次使用 [[Claude Code]] 时，建议手动执行一次 `/init` 指令。它的本质是让 Claude 扫描你的项目结构——识别你用的是 Python 还是 Node.js、用的是什么框架——然后将这些信息写入 `CLAUDE.md` 文件。

```bash
/init
```

执行 `/init` 后，根目录下会生成一个 `CLAUDE.md` 文件，这就是初始化成功的标志。而 `.claude/` 目录则不一定会出现，只有在进行自定义指令、项目级设置等高级操作时才会被创建。

> [!tip]
> 完成后立刻执行：
> - `git add CLAUDE.md`（提交项目规范）
> - 在 `.gitignore` 中添加 `.claude/`（排除本地缓存）

## CLAUDE.md：项目的"大脑"与"宪法"

`CLAUDE.md` 是项目上下文的核心载体，可以看作是项目的"长期记忆"和"操作手册"。如果不及时更新，每次启动 [[Claude Code]] 时 AI 都只能靠猜测来了解项目现状，容易导致生成的代码不符合最新规范。

### Git 管理策略

官方的 Git 管理建议很有区分度：

| 文件/目录 | 是否提交 Git | 理由 |
|-----------|--------------|------|
| `CLAUDE.md` | **应该提交** | 项目的"大脑"和"宪法"，提交后让团队成员获得一致的项目上下文和代码风格 |
| `.claude/` | **应该忽略** | 包含本地会话历史、设置快照及可能的敏感缓存数据 |

> [!danger]
> **安全提醒**：`.claude/` 目录可能包含 API 密钥或本地路径等敏感信息，绝对不应提交到公共仓库。

### CLAUDE.md 的最佳实践

官方推荐的长度控制在 **500 行以内**，只记录最重要的"规则"和"命令"。随着项目演进，`CLAUDE.md` 绝对需要持续更新——它不是一次性生成的静态文档，而是应该随项目一起演进的活文档。

更新方式有三种：

1. **使用 `/memory` 指令**：系统默认编辑器启动后手动修改
2. **自然语言指令**（最推荐）："请根据我刚刚添加的登录功能，更新 CLAUDE.md 中的关键目录说明和测试指令"
3. **使用 `#` 前缀指令**（快速增量更新）：`# 永远在修改代码后运行 npm test`

每次完成一个大的功能模块并准备提交代码之前，可以对 Claude 说："检查并更新 CLAUDE.md，确保它反映了当前的最新开发规范。"

## 常用指令速查

| 指令 | 作用 | 使用时机 |
|------|------|----------|
| `/init` | 生成 `CLAUDE.md` | 初次使用或项目结构大改后 |
| `/compact` | 总结对话并开启新窗口 | 对话太长、Claude 变得"糊涂"时 |
| `/config` | 修改 Claude 权限配置 | 需要调整是否允许自动执行命令时 |
| `/memory` | 编辑 memory 文件 | 需要手动修改 `CLAUDE.md` 时 |
| `/resume` | 恢复旧会话 | 需要基于历史对话继续工作 |

> [!tip]
> 当对话窗口已经非常长时，执行一次 `/compact` 会总结进度并让 Claude Code 带着"已完成"和"待完成"的清晰状态进入下一个阶段，既省钱（节省 Token）又提效。

## 复杂任务的标准工作流：五步法

面对复杂、多步骤的开发任务，官方推荐将需求编写成独立的 `.md` 或 `.txt` 文件（如 `requirements.md` 或 `task-v1.md`），然后遵循以下五步法：

1. **需求输入**：提供需求文档（如 `Read task-v1.md and implement the features described there.`）
2. **生成计划**：指令 Claude Code `"Create a detailed execution plan in plan.md for this task."`
3. **人工审核与修正**：打开 `plan.md` 检查步骤是否漏掉数据库迁移、是否破坏现有 API，有误直接修改或指令更新
4. **授权执行**：确认无误后指令 `"Execute the plan in plan.md step by step."`
5. **实时复核**：Claude Code 每完成一步检查结果，OK 了再让它进行下一步

> [!info]
> **plan.md 的 Git 策略**：
> - 临时任务计划：任务结束后删除
> - 重要架构变更计划：提交到 Git 作为项目文档的一部分

## 文件引用：`@` 语法与路径规范

[[Claude Code]] 提供了类似"提及"的语法来引用文件和目录：

```bash
# 使用 @ + Tab 键自动补全（推荐）
@plan        # 按 Tab 自动补全为 xx/yy/zz/plan.md

# 明确标识目录（需加尾部斜杠）
@src/utils/
```

官方建议使用**从项目根目录开始的相对路径**（即 `xx/yy/zz/aa.md`），而不是系统绝对路径。这是因为 Claude Code 的文件系统索引是从根目录向下生长的。

### 安全机制

Claude Code **不会扫描** `.gitignore` 中列出的文件及目录，这是基于双重考虑：

1. **安全**：防止 AI 意外读取并向服务器发送敏感数据（如日志中的密钥、本地数据库文件）
2. **性能**：避免盲目扫描 `node_modules` 等巨大目录导致索引过程崩溃

如果 `logs` 目录在 `.gitignore` 里，手动输入 `@logs/` 无法补全，按 Tab 键时它不会出现在候选项里。

### 中文文件名的已知限制

中文文件名的支持目前是一个已知痛点。由于 Unicode Search Bug，即使文件存在，输入中文关键词也往往无法触发 `@` 引用的匹配补全。

> [!warning]
> 如果项目中存在多个同名文件（如多个 `index.js` 或 `README.md`），不建议在提示词里只写文件名——Claude Code 可能会找错文件。使用 `@` + Tab 补全可以避免这个问题：能补全说明路径绝对正确，补不出说明权限受限或路径写错。

## 思考模式：何时开启"深度思考"

Claude Code 的思考模式应该在以下三种场景下开启：

1. **复杂逻辑/算法**：重构复杂的递归逻辑或处理并发冲突
2. **架构设计**：需要规划多个文件之间的调用关系时
3. **死活改不对的 Bug**：普通模式下 Claude 连续两次没修好时

可以通过 **Tab 键**在"标准模式"、"自动接受模式"和"计划模式"之间循环切换。如果需要单次最高级思考，可以在提示词开头加上 `ultrathink` 关键词——即便 Tab 关闭，本次对话也会以最大算力执行。

## 结语

掌握 [[Claude Code]] 的工作流不是关于记忆指令，而是理解其设计哲学：通过 `CLAUDE.md` 建立项目上下文，通过 `plan.md` 规划复杂任务，通过 `/compact` 保持对话清爽。配合 [[SpecStory]] 的历史管理，这套工具链能让 AI 辅助开发真正变得可追溯、可协作、可复制。

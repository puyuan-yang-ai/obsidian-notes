# 日志排查与系统诊断

当 OpenClaw 出现问题时，系统性的排查方法至关重要。本文介绍日志查看、内存诊断和常见问题排查技巧。

## 日志查看方法

### 方法一：journalctl 系统日志

```bash
journalctl --user -u openclaw-gateway -e --no-pager
```

### 方法二：直接查看日志文件

```bash
# 列出日志文件
ls -lah /tmp/openclaw

# 查看最近 200 行
tail -n 200 /tmp/openclaw/*.log
```

日志文件路径格式：`/tmp/openclaw/openclaw-<timestamps>.log`

## 状态检查命令

### `openclaw gateway status`

查看网关是否"在干活"：
- 运行状态：Running / Stopped / Error
- 连接情况：与 Telegram/WhatsApp 的连接状态
- 模型连接：是否能访问 AI 模型
- 版本信息：当前网关版本

**使用场景**：
- 机器人没反应时
- 修改配置后验证
- 排除网络故障
- 安装 Skill 后确认加载

### `openclaw status`

全局诊断工具，扫描整个安装环境检测潜在隐患。

**使用场景**：
- 遇到 `gateway closed (1006)` 等报错
- 安装 Skill 失败
- 功能报错但不崩溃

## 内存问题排查：OOM Killer

### 什么时候需要 dmesg

经验口诀：**程序突然 "Killed / 无报错退出 / 卡死"，第一件事看 dmesg**

```bash
dmesg -T | tail -n 80
```

- `dmesg` = display message（显示消息）
- `-T` 把时间戳转为可读时间
- `tail -n 80` 看最后 80 行

### 典型 OOM 场景

| 现象 | 可能原因 |
|------|----------|
| 终端只出现 `Killed` 或 `Terminated` | 90% 是 OOM Killer |
| npm/node/python/docker build 突然消失 | 高概率内存爆 |

> [!note]
> 代码报错、语法错误、npm 依赖冲突不需要用 dmesg——这些是应用层问题。

### 看到 Killed 后的排查流程

```bash
# 1. 查看哪个进程被杀
dmesg

# 2. 查看当前内存状态
free -h
```

## 内存管理：free 与 swap

### free -h 命令

`free` = show memory usage

**使用场景**：
- 怀疑 OOM
- 跑大任务前检查内存够不够

**最重要的字段**：`available`——还能安全用多少

### swap 机制

**全称**：Swap Space（交换空间）

**本质**：硬盘当作"临时内存备用池"

```
没 swap：RAM 满 → OOM → 杀进程
有 swap：RAM 满 → 把不常用内存页挪到磁盘 → 进程继续活着
```

> [!warning]
> Swap ≠ 提升性能，Swap = 保命机制
> 磁盘比内存慢 100~1000 倍，会变慢但不会死

### 内存状态解读

`free -h` 显示 `available = 517Mi, swap = 4G`：

> 还能直接用 500MB，不够就 spill 到 swap，系统不会 OOM

## sed 流编辑器

sed（Stream Editor）是强大的非交互式文本处理工具：

- 不打开文件界面
- 通过命令行逐行读取并修改文本
- 适合批量文本处理和脚本化操作

## 排查流程总结

```
问题出现
    ↓
1. openclaw gateway status（服务是否活着？）
    ↓
2. openclaw status（全局诊断）
    ↓
3. 查看日志（具体错误信息）
    ↓
4. dmesg + free -h（系统层问题）
    ↓
5. 定位问题并解决
```

---

掌握这些排查技巧，你可以在大多数情况下快速定位 OpenClaw 的问题根源，无论是配置错误、网络问题还是系统资源不足。

# 训练性能优化与底层原理

## GPU 训练的核心工作

理解 GPU 在训练中做什么，是优化性能的基础。每一步训练，GPU 做两件事：

### 1. 计算

执行矩阵乘法，包括：
- 前向传播：从输入到输出的计算
- 反向传播：梯度计算和参数更新

### 2. 搬数据

在显存中来回读写中间结果：
- 激活值（activation values）
- 梯度（gradients）
- 其他中间计算结果

这两个过程相互交织，共同决定了训练速度。

## 显存带宽的本质

### 显存带宽是硬件固定属性

显存带宽与模型大小没有关系，它是硬件的固定属性。就像高速公路的车道数是固定的，不会因为运的货多就自动变宽。

例如，MI308X 的显存带宽固定在约 5.3 TB/s，不管运行 0.5B 的模型还是 70B 的模型，带宽都是这个数。

### 模型大小如何影响带宽使用

虽然带宽本身不变，但模型大小会影响带宽的使用效率。一个常见的误解是：数据集一样，小模型和大模型如果 batch size 相同，每个 batch 所占的带宽也应该一样。

**实际情况恰恰相反**：同样的 batch size，大模型占的带宽远比小模型多。

### 带宽类比

可以这样理解带宽的使用：

- **公路宽度** = 显存带宽（MI308X: 5.3 TB/s，固定不变）
- **货物数量** = batch_size × 每条样本的激活值大小（这个取决于模型大小！）

GPU 搬运的不是原始数据（输入文本），而是模型计算过程中产生的中间结果（激活值）。

同一条文本，在不同模型里产出的中间结果大小完全不同：

- **Qwen 0.5B**：每条样本的激活值大小约 25 MB
- **LLaMA 70B**：每条样本的激活值大小约 4 GB

> [!info]
> **为什么大模型占用更多带宽**：
> - 搬运的主要是激活值，不是原始输入数据
> - 模型越大，每层产生的中间结果越多
> - 因此大模型即使使用相同 batch size，也会占用更多带宽

## 吞吐量优化

### 吞吐量的定义

吞吐量 = 每秒处理的样本数（samples/s），是衡量训练速度最直接的指标。吞吐量越高，训练越快。

### 如何达到最大吞吐量

**核心原则**：不要猜，要实测。

具体方法：

1. **精确的 benchmark**
   - 包含 warmup 阶段
   - 3 次测试取平均值

2. **测试不同 batch size**
   - 常见取值范围：[1, 2, 4, 8, 16, 32, 64]
   - 记录每个配置的：
     - 吞吐量 (samples/s)
     - 每样本耗时
     - 显存占用

3. **分析饱和点**
   - 通常在 bs=16 左右，GPU 效率已接近饱和（如 23.64 ms/sample）
   - 之后再加 batch 收益很小
   - 继续增加可能导致显存溢出

> [!tip]
> **Batch Size 优化策略**：
> - 从小开始逐步增加
> - 观察吞吐量何时不再明显提升
> - 在饱和点附近选择合适的值
> - 预留一定显存空间以应对峰值需求

## HuggingFace Trainer vs LLaMA Factory

### HuggingFace Trainer：训练积木/骨架

**特点**：
- 更底层，更通用
- 更容易理解本质
- 自己要管更多细节

**适合场景**：
- 想真正搞懂训练原理
- 想建立底层认知
- 想以后能独立 debug

**优势**：打地基，建立扎实的理解

### LLaMA Factory：训练脚手架/平台

**特点**：
- 封装更多
- 配置化更强
- 更适合快速实验
- 更适合 LoRA / QLoRA / 多模型切换

**适合场景**：
- 快速实验和迭代
- 利用社区现成配置
- 多模型对比测试

**优势**：快，省事，配置方便，社区例子多

### 关系与选择

LLaMA Factory 底层很多地方最终还是绕不开 HuggingFace 生态。因此建议的学习路径是：

1. 先用 HuggingFace Trainer 理解底层
2. 再看 LLaMA Factory 的封装
3. 根据实际需求选择工具

用 Trainer 不吃亏，反而是在打地基。很多行业同行使用 LLaMA Factory 是因为快速和便捷，但理解底层原理仍然重要。

## SFT 具体流程详解

基于 HuggingFace Trainer 的 SFT 训练流程包含以下步骤：

### 1. 原始监督数据（问答对）

结构化的 instruction-following 数据

### 2. 按模板拼接成训练文本

将 JSON 格式转换为训练用的文本格式

### 3. Tokenizer 分词编码

```
文本 → input_ids + labels
```

### 4. 构造 labels（最关键的一步）

```
input_ids: [User tokens][Assistant tokens]
labels:    [-100 ... -100][真实 assistant token ids]
```

**含义**：
- user 部分 label = -100 → 不计算 loss
- assistant 部分 label = 真实 token → 计算 loss

这确保了只在回答部分进行训练，这是 SFT 与预训练的关键区别。

### 5. DataCollator 组 batch

- Padding 到同一长度
- 生成 batch

**输出**：
```python
batch = {input_ids, attention_mask, labels}
```

### 6. 模型前向传播 forward

**模型输出**：
- logits：每个位置预测下一个 token 的概率分布
- loss：和 labels 比较后的交叉熵损失

### 7. Backward 反向传播

梯度从 assistant 部分的 loss 反传回模型参数

### 8. Optimizer 更新参数

根据梯度更新模型权重

> [!note]
> **SFT 与预训练的 Loss 计算区别**：
> - 预训练：全句都算 loss
> - SFT：只算回答部分 loss
> - 这个区别通过 labels 中的 -100 标记实现

## 关键概念总结

### Teacher Forcing 细节

在训练中，模型每一步不是吃自己刚生成的词，而是吃真实答案中的前文 token。这种机制：

- 避免了错误累积
- 加速了训练过程
- 提高了训练稳定性

### 从底层到高层的选择

理解了这些底层原理后，无论选择 HuggingFace Trainer 还是 LLaMA Factory，都能：

- 更好地调试问题
- 更准确地优化性能
- 更深入地理解训练过程

底层知识是所有高层工具的基础，投入时间理解这些原理是值得的。

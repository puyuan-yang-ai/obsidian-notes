# RAG 混合检索：从 RRF 融合到 Rerank 精排序

## 混合检索的动机

> [!danger]
> **纯语义检索的致命缺陷**
>
> 语义检索返回的都是**通用的建议**而不是针对性的建议。通用建议往往得分高但价值低。

更严重的问题是，语义相似度检索**无法识别互斥性信息**。例如 HIP 和 CUDA 是互斥的，但在语义空间里两者是相近的，导致检索结果里出现误导性的建议。

## 两路召回：稠密与稀疏的互补

混合检索集成两方面的优点：

| 检索类型 | 偏向方向 |
|----------|----------|
| 稠密检索（Embedding） | 更偏"语义像不像" |
| 稀疏检索（BM25） | 更偏"关键词是否出现""

### BM25 索引的粒度选择

> [!question]
> **BM25 索引应该建在文档级别还是 Chunk 级别？**
>
> **Chunk 级别（推荐）**

| 级别 | 问题 |
|------|------|
| 文档级别 | 检索到整个文档还要二次定位；与语义检索粒度不一致，融合困难；实现复杂 |
| Chunk 级别 | 直接返回相关段落；粒度一致，融合简单；实现简单 |

## 融合策略：加权分数 vs RRF

### 加权分数融合的问题

```python
# 分数尺度不一致
语义相似度：0-1
BM25 分数：0-50+
```

这导致需要归一化，增加实现复杂度，且归一化方法会影响结果。

### RRF：业界标准的选择

> [!success]
> **RRF（Reciprocal Rank Fusion）的三大优点**
>
> 1. **只看排名，不依赖原始分数**：天然避免尺度问题
> 2. **业界标准**：Elasticsearch、Pinecone、Weaviate 都用这个
> 3. **可加权**：通过加权 RRF 公式实现 7:3 等比例

RRF 公式：

```python
score = weight / (rrf_k + rank + 1)
```

常见配置：`semantic_weight=0.7`, `bm25_weight=0.3`, `rrf_k=60`

## RRF 融合的执行流程

> [!warning]
> **误区：不是"先去重再计算"**
>
> 而是**"边遍历边去重边累加"**

```
Step 1: 语义检索召回 25 个
       → 遍历，每个 chunk 计算语义 RRF 分，存入 scores{}

Step 2: BM25 检索召回 25 个
       → 遍历，每个 chunk:
          - 如果已在 scores{} 中 → 分数叠加（重叠 chunk）
          - 如果不在 scores{} 中 → 新增（独有 chunk）

Step 3: 按融合分数排序，取 top 15
```

### 重叠 Chunk 的双重加成

如果一个 chunk 同时出现在语义 Top 5 和 BM25 Top 5：

```
分数 = 语义高分 + BM25 高分 → 双重加成
```

这正是 RRF 的设计意图：**两路都认可的结果排更前**。

### 候选池的实际大小

两路各召回 25 个，最后的结果不一定是 50 个：

```
25 ≤ 候选数 ≤ 50
```

取决于两路重叠程度。

## RRF 得分的正确理解

> [!danger]
> **常见困惑：RRF 分数这么低？**
>
> 纯语义检索得分是余弦相似度，范围是 0~1，通常 0.8 以上。
>
> RRF 融合得分是排名倒数加权，范围很小，0.016 已经是"排名非常靠前"。

| 得分类型 | 算法 | 范围 | 含义 |
|----------|------|------|------|
| 语义相似度 | 余弦相似度 | 0~1 | 向量相似程度 |
| RRF 融合 | 排名倒数加权 | 很小 | 综合排名得分 |

**RRF 分数不是"相似度"，而是"综合排名得分"**。

## 融合后的分数只是粗排序

混合检索融合后的分数只能算是**粗排序**，它不擅长做"多约束条件的精确判别"。

典型场景：看起来都在讲向量化，但只有一条真的适用于 bf16 + MI308 + 你的访问模式。

## Rerank：精排序的关键

> [!tip]
> **Rerank 的核心价值**
>
> 正确 chunk 原来在 11–40 名，而 rerank 能把它拉进 Top 8。

### Rerank 的输入输出规模

经验上 rerank 的输入常见量级是 50–100，输出默认 Top 8 很稳：

```
50（rerank 输入）→ 8（LLM 上下文）
```

### 为什么中间不需要手动裁剪

> [!danger]
> **提前裁到 20/30 的问题**
>
> reranker 还没出手，关键 chunk 已经在 embedding 阶段被误杀。

双路召回合并后约 50 个，直接整体送进 reranker，中间通常不再手动裁到 20/30。原因：

1. 很多系统的 recall 提升，正是来自："关键 chunk 排名原来在 30~60 名，被 reranker 拉到前 5"
2. reranker 的设计输入规模本来就是几十到上百（bge-reranker-large 推荐输入规模是 32–100）
3. 50 是非常健康的甜点区间：效果好，成本可控，延迟稳定

### Rerank 输出的一致性

> [!info]
> **Rerank 与输入顺序无关**
>
> 同一批候选文档集合 → 不管输入顺序如何 → reranker 输出的排序应当一致

reranker 本身不需要依赖你前面的排序。每个 doc 的分数只取决于 `(query, doc)`，与"它在列表中是第几个"无关，不存在"文档之间相互比较"的依赖。

## 完整检索链路

```
25（稀疏/BM25）+ 25（稠密/Dense）→ RRF 融合 → 50 候选 → rerank → 8（送给 LLM）
```

## 何时调整召回参数

当前双路召回各 25 个（25+25）：

| 场景 | 建议 |
|------|------|
| 候选 50 里经常找不到正确 chunk | 加到 30/30 或 40/40 |
| 候选里基本都有，只是排序不对 | 提单路 K 意义不大，应该优化 rerank 或 filter |

## RAG 检索优化的解决思路

当遇到 **RAG 检索到的输出有误导、Top10 不稳** 时：

> [!success]
> **推荐思路**
>
> **先 reranker，后 filter（遇到瓶颈再做）**

先上 reranker，先把"排序不稳/被噪声带偏"这类问题解决掉，等到真的遇到瓶颈（效果、延迟、成本、稳定性）再考虑 metadata filter。

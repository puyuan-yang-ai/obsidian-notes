# OpenClaw 的记忆系统设计与文件加载机制

OpenClaw 的记忆管理系统是其智能化能力的核心基础，通过巧妙地区分长期记忆与短期记忆，模拟人脑的遗忘曲线，在保障信息安全的前提下实现了高效的上下文管理。

## 长期记忆与短期记忆的差异化设计

OpenClaw 将记忆系统分为两个层级：长期记忆（MEMORY.md）和短期记忆（memory/YYYY-MM-DD.md）。

**MEMORY.md** 承载的是经过提炼的知识和决策，而非原始日志。这些内容跨多个 session 仍然有效，包括关键决策、长期配置偏好、沉淀下来的经验教训等。出于安全考虑，MEMORY.md 仅在主会话（直接私聊）中加载，群聊环境下不会自动读取，这有效防止了私人信息的泄露风险。

相比之下，**memory/YYYY-MM-DD.md** 按日期组织原始记录，记录每日的原始过程与临时思考。系统会自动读取今天和昨天的文件，形成一个 2 天的滑动窗口，类似于人脑的短期记忆机制。这种设计确保了近期信息的直接可用性，同时避免了上下文过载。

## 会话启动时的文件加载策略

每次会话启动时，OpenClaw 会根据会话类型执行不同的加载策略。对于所有会话，系统都会读取 **SOUL.md**（身份定义）、**USER.md**（用户信息）和最近两天的 **memory/YYYY-MM-DD.md**。如果是主会话，系统会额外读取 **MEMORY.md**。

> [!info]
> **会话类型判断规则**：
> - 直接通过 Telegram 和 OpenClaw 对话（无论是私聊还是群组的 topic）都算主会话
> - 通过 sessions_spawn 创建的子智能体所产生的会话才是子会话

非主会话（如子会话、agent:xxx 或 isolated）启动时，默认不会读取 MEMORY.md 或 memory/YYYY-MM-DD.md 等记忆文件。这是出于安全考虑，防止主会话中的私人信息被自动带入后台任务。唯一的例外是，子会话可以通过 sessions_history 工具主动获取主会话的聊天记录，但仍不会自动加载记忆文件。

更早的日志文件不会自动加载，如需访问则需要通过检索工具查找。这种设计类似人脑的遗忘曲线：近期信息直接保留在短期记忆，重要信息沉淀到长期记忆，而久远的记录需要主动"回忆"才能调取。

## Telegram 环境下的记忆加载机制

在 Telegram 群组和 topic 下，MEMORY.md 不会被加载。这是因为 Telegram 群组和 topic 属于"group chats"或"shared contexts"，不属于主对话。只有 Telegram 私聊才是主会话，才会加载 MEMORY.md。

设计目的非常明确：防止私人信息泄露。MEMORY.md 可能包含个人偏好、敏感配置等内容，不应在群聊中暴露，因此系统只在"一对一直接对话"中加载这些信息，确保写在 MEMORY.md 里的敏感或个人内容不会无意间泄露到子任务或群组环境中。

## 会话历史的持久化存储

所有对话的会话历史信息都被持久化存储在 **~/.openclaw/agents/main/sessions/** 路径下，文件格式为 **.jsonl**（每行一个 JSON 对象）。这种设计确保了会话状态的可追溯性和可恢复性，即使系统重启，也能够恢复完整的对话上下文。

## 触发机制的差异化设计

主会话和子会话的触发方式存在本质差异。主会话由用户发消息触发，向主 agent 发送内容时就会进入主会话流程。子会话则通过 **sessions_spawn** 命令启动，用于创建一个独立运行的子 agent。

整体流程是：主会话接收用户指令 → 通过 sessions_spawn 创建子会话 → 子会话独立执行 → 完成后向主会话汇报结果。子会话在后台执行具体任务，与主会话上下文隔离，这种设计既保证了任务的并行执行能力，又维护了信息安全的边界。

通过这种分层设计，OpenClaw 在保障信息安全的前提下，实现了高效的记忆管理和上下文调度，为智能体的持续运行提供了坚实的基础。

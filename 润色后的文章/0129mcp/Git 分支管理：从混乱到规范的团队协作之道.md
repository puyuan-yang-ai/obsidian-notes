# Git 分支管理：从混乱到规范的团队协作之道

## Git 的去中心化设计理念

在理解分支管理之前，需要先理解 Git 的核心设计哲学：**Git 是一个去中心化的版本控制系统**。

> [!info]
> **Git 分支无主次之分**
>
> - 任何分支都可以合并到任何分支，没有"主次"之分
> - A 合并到 B ✅，B 合并到 C ✅，C 再合并回 A ✅，甚至循环合并 ✅
> - Git 只关心提交历史的有向无环图 (DAG)，不关心分支的"身份"

这种灵活性是 Git 的强大之处，但也意味着如果没有规范约束，团队协作很容易陷入混乱。

## 混乱的现实：缺乏规范的后果

当团队没有建立清晰的分支管理策略时，会出现一系列问题：

> [!danger]
> **不规范导致的问题**
> - 不知道哪个分支是"最新的"，开发时不知道基于哪里
> - 合并方向混乱：A→B→C→A 循环合并，历史难以追溯
> - 多人并行开发时，代码冲突频繁且难以解决

## 实战案例：分支合并困境

假设你正在 `rag_summarize_original` 分支上工作（这是同事的分支，他之前合并过你的分支），而你自己的分支是 `feature/bge-chunker-extended-kb`。现在需要开发 reranker 模块，应该基于哪里？

> [!tip]
> **解决步骤**
> 1. 先搞清楚分支差异：`git log --oneline --graph --all`
> 2. 选择更完整的分支作为基础
> 3. 创建新分支来开发 reranker，不要直接在现有分支上改

## 建立长期的团队规范

要避免混乱，需要建立清晰的分支管理规范：

> [!success]
> **团队协作三原则**
>
> **1. 确定主分支**
> - 指定 `main` 或 `develop` 作为"真相之源" (Source of Truth)
> - 所有开发基于主分支进行
>
> **2. 明确合并方向**
> - 只允许 `feature → develop`，不允许反向合并
> - 保持合并方向的单向流动，避免循环依赖
>
> **3. 使用 Pull Request**
> - 即使不做 code review，PR 也能记录合并历史
> - PR 提供了代码变更的审计追踪

这种规范的核心是**建立"真相之源"**：团队中有一个分支永远代表"最新的、可部署的代码状态"，其他所有分支都从这里派生，最终合并回来。

# RAG 架构实战：混合检索与模型选型完全指南

## RAG 检索流程：从粗排到精排

现代 RAG 系统的标准架构采用"粗排 → 精排"范式，充分发挥不同模型的优势。

### 无 Rerank 的基础流程

在未引入 Reranker 的情况下，检索流程相对简单：

```
稀疏检索 25 + 稠密检索 25 → 去重 → 融合打分 (RRF) → 按融合分排序 → 取 Top 15 → 给 LLM
```

> [!info]
> **混合检索的融合策略**
>
> 主流使用 **RRF (Reciprocal Rank Fusion)** 策略：
> - 按各自排名的倒数加权求和
> - 公式：`score = Σ 1/(k + rank_i)`，通常 k=60
> - 对异常值鲁棒，不需要参数调优

### Bi-Encoder vs Cross-Encoder

理解这两种编码器的差异，是掌握 RAG 架构的关键：

| 模型 | 使用阶段 | 工作方式 | 特点 |
|------|----------|----------|------|
| **Bi-Encoder** | 检索阶段（粗排）| Query 和 Document 分别编码，计算相似度 | 快速、可预编码、适合大规模检索 |
| **Cross-Encoder** | Rerank 阶段（精排）| Query + Document 拼接后一起过模型 | 能捕捉更细粒度的语义交互，但计算量大 |

### 引入 Reranker 后的正确流程

> [!danger]
> **常见错误：过早截断**
>
> ❌ 错误流程：
> ```
> Semantic 25 + BM25 25 → RRF 融合 → 截断到 15 → Reranker → Top 8
> ```
>
> ✅ 正确流程：
> ```
> Semantic 25 + BM25 25 → RRF 融合（去重）→ 全部送给 Reranker → Top 8
> ```

为什么不应该在 Reranker 之前截断？

> [!tip]
> **保留足够候选给精排**
>
> - RRF 是粗排，语义理解能力远不如 Reranker
> - 可能丢失融合后排名 16+ 的高质量结果
> - Chunk P 虽然 RRF 分数排第 16（词频不高），但语义超相关
> - 如果截断到 Top 15，Reranker 没机会识别出最佳答案

**混合检索层已完成基于对象 ID 的去重**，每个 chunk 对象最多出现 1 次，可以放心全部送入 Reranker。

## Embedding 模型选型：通才 vs 专才

### 主流 Embedding 模型概览

**BGE-M3** 是当前多语言 RAG 的默认首选，支持 100+ 语言，最大上下文 8192 tokens。

不同场景的模型选择：

| 场景 | 推荐模型 | 原因 |
|------|----------|------|
| 英文 RAG | `bge-large-en-v1.5` | 更快、更轻、英文专优 |
| 多语言 RAG | `bge-m3` | 100+ 语言支持 |
| 长文档检索 | `bge-m3` | 8192 tokens vs 512 |

### 实际案例：是否需要切换模型？

对于 `amd-ai-devtool` 项目，使用 `bge-large-en-v1.5` 是否应该换成 `bge-m3`？

> [!warning]
> **不需要换，原因如下**
>
> - 项目是英文检索任务，`bge-m3` 没有优势甚至可能略差
> - `bge-m3` 训练目标是多语言通用性，牺牲了英文专用性能
> - 这是典型的"通才 vs 专才"权衡

**什么情况才考虑换模型？**

1. 需要中文/日文支持（如加入中文 ROCm 文档，提升可达 +30-50%）
2. 文档超长（如完整的 API 规范 > 5000 tokens，`bge-m3` 的 8192 tokens 才有意义）
3. 需要内置 sparse 检索（但如果有优化过的 BM25，没必要）

## Reranker 模型选型：精度 vs 速度

### bge-reranker-v2-m3 vs bge-reranker-v2-gemma

这两个模型如何选择？答案很明确：**默认选 m3**。

| 对比维度 | bge-reranker-v2-m3 | bge-reranker-v2-gemma |
|----------|-------------------|----------------------|
| 速度 | 0.5 秒 | 20-30 秒（慢 40-60 倍！）|
| 显存占用 | 2-3GB | 4-5GB |
| 模型大小 | 1.2GB | 2GB |
| 定位 | 主流工程解 | 精度优先 + 资源充足 |

> [!success]
> **选 m3 的五大理由**
>
> 1. 实施难度一样：只是改个模型名，零难度差异
> 2. 速度快 40-60 倍：用户体验天壤之别
> 3. 显存占用少：降低 OOM 风险
> 4. 稳定性更好：成熟模型，社区反馈好
> 5. 模型更小：下载和加载更快

**最佳实践**：大多数请求用 m3，少量高价值/高风险请求（或离线评测）用 gemma。

## 标准三段式 RAG 架构

```
┌──────────────────────────────────────┐
│ Embedding: bge-large-en-v1.5         │ ← 英文专优
├──────────────────────────────────────┤
│ Hybrid Search:                       │
│  - Semantic (0.7)                    │ ← 语义检索
│  - BM25 (0.3)                        │ ← 关键词检索
│  - RRF Fusion (k=60)                 │ ← 融合算法
├──────────────────────────────────────┤
│ Reranker: bge-reranker-v2-m3         │ ← 精排
└──────────────────────────────────────┘
```

## RAG 系统评估维度

评估一个 RAG 系统的质量，需要从多个维度考虑：

- **Query 质量**：用户查询是否清晰、具体
- **检索质量**：召回率和准确率的平衡
- **Reranker 效果**：精排是否真正提升了相关性
- **对最后结果的价值**：是否真正改善了用户体验

粗排不要截断太狠，精排才是最终决策者，应该有足够的选择空间。
